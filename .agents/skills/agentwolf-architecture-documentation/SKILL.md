# AgentWolf 架构文档开发

从当前源码提炼可供研发人员理解、评审和修改系统的架构设计。文档需要解释系统为何以当前方式
组成、各部分如何协作以及哪些边界必须保持，不能退化为目录索引、实现清单或行为流水账。

## 建立事实模型

1. 阅读从仓库根到目标文档目录的 `AGENTS.md`，以及
   [当前态交付物纯净性规则](../../../artifacts_rules.md)。
2. 检查工作树和最近相关 diff，区分当前实现、历史材料与未来设想。
3. 从公共入口开始，沿配置、Schema、数据、控制、事件、状态和恢复路径阅读源码与测试。跨包行为
   至少核对 producer、owner 和 consumer，不能只根据现有文档改写。
4. 把事实归纳为职责、契约、依赖方向、生命周期和不变量。文件名与类名只保留到足以定位稳定
   所有者的粒度。

按职责域选择源码入口：规则行为从 `GameEngine` 与 Ruleset registries 向外追踪；对局编排从
`MatchManager`、`MatchRuntime` 与 repositories 追踪；模型回合从 `ContextRenderer`、
`PlayerRuntime` 与 ACP Session 追踪；浏览器行为从 contracts DTO、server projector 与 Web hooks
双向核对。涉及可见性时，同时检查事件可见性、phase 投影和最终 DTO。

## 选择文档粒度

- 系统架构说明外部边界、主要子系统、端到端运行链路和跨模块状态所有权，并将专项机制链接到
  对应子文档。
- 专项架构深入一个稳定职责域，说明内部组件协作及与上下游的契约，不展开逐函数实现。
- Package README 拥有包内 API、失败模式和限制；Schema、生成目录、测试与开发 Skill 拥有精确
  字段、清单、验证和操作步骤。架构文档通过链接引用这些所有者。

开始写作前阅读[架构文档模板](references/architecture-document-template.md)。模板规定必须回答的
设计问题和图表选择，不要求机械复制标题。

## 写作与制图

- 使用中文、当前时态和当前有效系统，先写目标、约束与边界，再写组件及流程。
- 组件描述同时交代其决策或状态、输入输出、依赖方向和失败边界。
- 使用 Mermaid 表达仅靠文字不易看清的关系。每张图只回答一个主要问题，并在正文解释关键边界
  或状态转换。
- 系统文档通常需要系统上下文图、组件关系图和一条端到端时序；专项文档只增加能解释其独有机制
  的组件图、流程图、时序图或状态图。
- 图中使用职责名称。只有正式契约或定位所有者所必需时才使用类名；不得用文件树、类继承树或
  与正文重复的装饰图冒充研发制图。
- `docs/architecture.md` 与 `docs/architecture/*.md` 每份不超过 500 行。上限不是内容目标；能由
  稳定链接承载的细节不复制。

## 完成检查

- 每项设计陈述都能由当前源码、Schema、配置、迁移或测试支持。
- 文档能回答系统边界、关键组件、主要运行流、状态归属、并发/恢复语义、故障边界和扩展位置。
- 隐私、持久 Session、事件重放、barrier 等不变量在其唯一权威文档中明确出现，其他文档只链接。
- 不包含迁移叙事、废弃方案、讨论过程、调试记录、交付日志、未来路线图或未落地能力。
- 主文档与专项文档分工明确，图表互补，术语和依赖方向一致。
- 相对链接按精确大小写有效，Skill 通过 `quick_validate.py`，文档通过 `pnpm check:docs` 与
  `git diff --check`。纯文档工作不需要运行游戏、启动 Agent 或执行浏览器验收。
